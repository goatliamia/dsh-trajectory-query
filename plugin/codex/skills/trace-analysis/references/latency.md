# 耗时与等待

先明确要缩短的是首个可用结果、某次操作，还是整段任务完成时间。选相应工作段，还原请求、工具执行、状态查询、子任务与后续处理的时间关系。

**找到实际挡住推进的依赖。** 从结果往前追：完成它必须等哪些结果，哪些工作已经重叠，哪些只是发生在同一时段。父调用包含子调用、并行分支相互覆盖时，分别看整体等待和内部执行。优先处理缩短后能使关键后续动作提前的部分。

**判断慢来自哪种组织方式。**

- 单次长阻塞：检查工具在处理什么、返回何时已经足够采取下一步，是否有更早取得关键结果的方式。
- 多次短往返：检查本可一次取得的独立信息是否被逐项请求，每次模型介入是否确实需要新的判断。
- 状态等待：检查是否复用了已有任务、状态查询是否带来新信息，以及等待期间有没有可独立推进的工作。
- 子任务衔接：检查是否因启动太晚、交付条件不清、重复调查或等待无关分支拖慢汇总。
- 返工和晚验证：检查前面的哪个遗漏把错误推迟到昂贵阶段才暴露。

有请求分段计量时，再比较响应前等待、生成和工具执行；未分解的剩余时间不统一命名为“思考慢”。若输出生成占主要时间，检查这些输出承担了哪些工作，以及是否反复汇报已有内容。

并行建议要指出可独立的输入、产物和汇合点，并考虑共享资源或修改冲突。验证重点是关键后续是否真的提前、首个可用结果是否更早，以及是否因并发或改变验证顺序增加返工。
