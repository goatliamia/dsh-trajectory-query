诊断这次工作怎样取得结果、哪些投入有价值、哪些做法拖累了推进，以及下次先改什么。使用全部可取得的运行证据；用户指定问题时直接深入，不必遍历所有主题。

## 综合诊断

**把任务、过程和结果放在一起。** 先确认用户要求的产物、关键约束和验收条件，再看实际交付及验证。按工作目的或关键状态变化划分阶段，例如定位、实现、验证、恢复；同一阶段可以跨多轮或包含子任务。区分需求变化带来的新增工作、任务本身的难度和可以避免的返工。模型说“已完成”与已有产物、验证结果分别核对。

**看投入怎样变成进展。** 对照阶段投入和关键转折：有没有获得决定性信息、排除路线、形成可用产物或完成必要验收。既找单次长阻塞，也找贯穿多轮的短等待、重复供给和恢复负担。把探索、准备和验证放回后续用途，判断它们是否减少了后面的风险或工作。

**从值得解释的现象追到可调整的原因。** 围绕同一个问题串起“当时掌握什么—采取什么动作—得到什么反馈—怎样处理—结果怎样”。从明显损失往前追，找到仍有机会改变后续的环节：前提缺失、工具选择或参数、反馈利用、状态交接、环境限制，还是验收太晚。结合当时已经可用的信息判断，不要求模型提前知道后来才暴露的事实。选择相近的成功尝试、前后阶段或不同对象作对照，检查解释能否同时说明它们的差异。

**选能改变下一次工作的建议。** 对每个主要问题，想清楚：如果改变这个动作、材料供给或任务安排，后面哪段等待、补查或返工会减少，什么必要能力仍需保留。优先考虑影响范围大、重复发生、改变成本低的环节。证据支持流程判断时可以先提出改法，精确收益交给验证。

### 验证改法

先明确应保持的任务结果，以及预期减少的具体负担。能复现的问题先验证原失败是否消失；涉及通用策略或能力配置时，再选正常任务和可能受损的边界、恢复场景作对照。尽量保持初始任务、环境及其他配置一致，检查完成质量，再比较完成时间、总用量、补读、返工或人工接手。单次成功用于确认这一例，普遍收益需要多例支持。

## 专项方法

只读取当前问题需要的方法；涉及多个因素时联合分析。

| 深入的问题 | 方法 |
| --- | --- |
| 时间被什么挡住，怎样更早取得结果 | [耗时与等待](references/latency.md) |
| 哪些投入持续增加开销，怎样保留能力地调整 | [用量与能力投入](references/cost.md) |
| 尝试有没有进展，反馈为何没有被用上 | [反复尝试](references/repeats.md) |
| 查找、读取、修改是否支持了正确判断 | [工具与文件使用](references/io.md) |
| 材料如何保留、更新和恢复，是否支持后续工作 | [上下文持续使用](references/context.md) |

交付按[报告写作](../../../../report/WRITING.md)组织。

未连接取证工具时，用 Node 运行本目录相对路径 `../../../../scripts/trajectory-query.mjs --host codex --request <args.json>`；默认当前会话，指定会话加 `--thread ID`。工具声明用 `--tool schema` 获取。

需要 HTML 报告时读[组件用法](../../../../report/AUTHORING.md)；其中报告 CLI 位于本目录相对路径 `../../../../scripts/trajectory-report.mjs`。
