# 诊断方法与工具设计复盘

日期：2026-10-30。状态：核心能力进入工具 0.5.0 后完成三会话再试，见 [本轮实验](diagnostic-experiment-v3-results.md)。收尾版本 0.5.1 已安装到本机 DSH，插件组件运行中。本文保留设计取舍；当前使用与范围见 [诊断入口](diagnostics.md)。

关联材料：[v2 草稿](diagnostic-analysis-v2.md)、[试跑记录](diagnostic-pilot-results.md)。v2 的可定位性检查和实际工具缺陷仍可参考，但报告的诊断价值没有达到用户要求，不能把“三份报告完成”当作方案有效。

## 1. 项目应交付什么

把 Agent Trace 和 Eval 的专业方法转成用户能做决定的信息：这次工作主要怎么推进，哪些投入值得，什么做法拖累了推进，下次先改什么，以及怎样知道改得对。

统计量回答“发生了多少”；原文回答“当时做了什么”；诊断还要回答“这对任务意味着什么，值得改变什么”。准确引用是基本条件，不能代替后两项。

不能把任务复杂、产物多、必要校验多简单诊断成低效。观察到具体流程问题，可以提出有理由的改法；建议的精确收益再由验证决定。缺少逐条因果归属时，仍可在来源、工作阶段或流程层面形成判断。

用户需要的是少量重要判断。分析应优先解释主要投入、主要阻塞或影响验收的风险，不以异常条目数、引用数或报告篇幅衡量价值。

## 2. 此次失败教会了什么

1. **固定排行榜改变了调查方向。** 先看到耗时最长、返回最大或重复最多的孤立条目，就容易围绕这些条目做审计，忽略全程反复发生的小负担、实际任务目标和关键转折。总览需要提供过程和投入分布。
2. **限制推断的文字多，正面方法少。** 提示词需要教模型比较什么、如何判断推进、如何把发现转成改法。把所有不确定性逐项写进正文，会挤掉真正的解释。
3. **证据阅读单位过小。** 相邻几条 seq 不一定包含同一次操作的调用、完整状态、正式返回和后续处理。单条返回短，不代表总工作量小。
4. **事实正确与诊断有用被混在一起验收。** 试跑核对了引用，却没有充分检验选题重要性、解释力和建议是否改变下一次行动。
5. **不能把本地桥缺口都算成产品缺口。** 原生 reads、graph 已存在。需要先改善它们的内容和衔接，不按试跑脚本的动作数增造工具。

这些是对方法与产品设计的复盘，不是对三个会话重新下结论。

诊断的基本单位应是一段为解决同一问题所做的尝试：带着什么问题行动、得到什么反馈、下一步怎样变化。原始事件是证据位置；单个步骤的数字只是这段过程的一部分。一次异常是否重要，要放回主要投入、发生频率、后续连锁影响和结果要求中判断。

## 3. 专业知识如何进入五类分析

五类分析共享全部可用数据。上下文构成、组装、投递、回执作为解释过程的共同剖面；Skill、插件、工具、文件作为聚焦对象。

| 用户的问题 | 真正需要教给模型的方法 | 用户最终据此做的决定 | 改法的验证重点 |
|---|---|---|---|
| 为什么慢 | 先找时间集中在哪些工作阶段，再区分一次长阻塞、短等待累积、返工和必要校验；根据实际依赖判断哪些等待处在推进路径上 | 先调整哪段调用、任务安排、等待或状态处理 | 相同任务验收下的等待与完成时间；是否增加错误、返工或人工处理 |
| 为什么贵 | 区分实际输入/输出、固定能力负担、随历史增长的负担和额外调用；看负担持续多久、能否通过缓存复用，以及这些能力怎样被发现和使用 | 精简哪种内容、怎样供给工具或材料、在哪个阶段调整配置 | 真实 usage 与能力可发现性；新增查找、参数错误和补读是否抵消收益 |
| 是否绕圈 | 围绕一个未解决问题串联尝试：前提是什么、反馈是什么、下一次改了什么、是否获得新信息或更接近验收 | 继续哪条路线，先补什么信息，什么时候换方法 | 是否解决原问题；同类失败、无进展尝试和误停止是否减少 |
| 工具与文件怎么用 | 从信息需求看能力选择、范围、返回和后续采用；比较早期小范围定位与必要的深入阅读，检查版本和实际覆盖 | 改哪一步发现、搜索、读取、调用或返回结构 | 所需依据是否取得；遗漏、补读、错误和总工作量是否改善 |
| 长上下文怎样持续工作 | 将材料的积累与当前任务联系起来：哪些是长期约束、当前状态、可再取证据；观察更新、压缩和交接后是否保留继续工作的条件 | 哪些内容留在上下文、哪些外置、交接应保留什么、何时更新 | 后续是否能正确继续；约束遗漏、恢复成本和总消耗怎样变化 |

这里的“阶段”由模型结合用户要求、行动和产物理解。工具提供时间顺序与统计，不在后台另调模型自动给阶段命名，也不伪造任务完成率。

每种场景方法应交代五件事：要帮助用户做的决定、典型的过程模式、怎样对照解释、可改变的对象、验证改法时要保持的任务结果。共同计量规则集中维护，不在五份方法里重复。

改法有不同层次：一次调用的参数/状态处理、一段任务的工作方法、持续使用的能力与材料供给。只抓到一个孤立调用时，不把结论扩大成全程策略；若同一做法贯穿多个阶段，则应讨论流程，而不只修补一次调用。专业分析需要选对这个层次。

### 成本场景要特别关注能力供给

后续约束：静态剖面同时解释构成、实际使用与能力价值，见 [静态剖面设计及 dsh-ops 对照](static-context-profile.md)。工具较大、返回较多或近期未调用本身不支持替换；涉及加载或执行语义变化的建议，需说明具体能力差异与受影响场景，并保持用户需要的任务结果。

“定义很大但调用少”只能作为调查起点。下一步要看：该组能力以 schema 还是 Code Mode 目录提供，是否长期稳定存在，任务实际需要什么，获得完整签名是否容易，配置变化是否反复改写稳定输入。

可比较的供给方式包括精简定义、按任务准备工具集、可靠的延期加载、简要索引加按需详情。比较时同时保留能力完整性和发现成本。固定定义估算、上下文存量与逐请求实际用量分别使用，不能把一个估算乘上元数据事件数当作累计费用。

这同样约束我们自己的工具：诊断插件不应常驻五份长方法、数十种细分接口和重复参数说明。

## 4. 方法必须可执行，但不应写成固定审计表

建议采用以下调查逻辑，按实际问题跳转：

1. **形成任务画像。** 结合用户要求、阶段性产物与验收，理解在做什么；用总览观察投入的集中和分散。用户指定局部问题时，直接进入局部，再补必要背景。
2. **提出值得验证的解释。** 例如主要等待来自哪段串行依赖，某种材料为什么反复取回，能力发现是否给多个阶段增加了重复工作。解释应能帮助选择改法。
3. **查询能区分解释的证据。** 选择范围和对象，读有关联的动作、反馈和后续结果；需要时查看上下文剖面。每次补查应能改变优先级、建议或验证方式。
4. **给出工作判断。** 说明主要问题、影响范围及优先调整对象。精确比例缺失时，可以判断流程值得改变；收益大小另作验证。
5. **提出最小有用验证。** 有些建议只需复现一次失败再检查修复；有些需要同类任务对照。只有要估计普遍收益时，才扩大到更多任务和重复运行。

这些不是五个必须分别调用的工具步骤。一次结果已提供足够信息时，直接形成判断；问题复杂时允许继续调查。停止条件是下一项查询难以改变用户要做的决定，而不是收齐所有主题。

## 5. 采用用户指定的 agent-experience 原则

依据已安装的 `@deepseek-ai/dsh-agent-preset/skills/agent-experience/SKILL.md`：

| 原则 | 在本项目中的具体取舍 |
|---|---|
| Start with minimal context | 工具常驻说明只包含用途、可选动作和关键参数；场景方法按需取得 |
| Make discovery explicit | 延后加载的方法、正文和细节有清楚描述及直接可用的读取参数；不靠模型猜路径或参数 |
| Prefer bounded outputs | 返回有界总览、统计和执行片段；明确省略量与续读入口 |
| Use locality | 查询某次操作时，一起提供大概率需要的起因、调用、状态/反馈和后续处理，而不只给固定 seq 邻居 |
| Evaluate total work | 同时看首次工具定义负担、整次分析用量、补读、查询和错误；不单看每条返回变短 |
| Say each fact once | 用途、参数规则、共同口径、场景方法各有一个维护位置；分页不重复全文说明 |
| Describe behavior, not implementation | 模型只需知道能取得什么；内部投影、解析、哈希校验与缓存机制不进入日常使用说明 |

参数合法组合和默认值要在可取得的参数契约中说明。不能依赖模型先传错、再从报错发现有哪些能力；也不应要求每次分析先调用一个冗长的 help。

## 6. 工具边界：沿用现有四入口

| 入口 | 继续负责什么 | 本次设计要改什么 |
|---|---|---|
| `trajectory_search` | 找会话、字面事件和已知对象的位置 | 为不认识的对象定位；保持与诊断统计的边界清楚 |
| `trajectory_inspect` | 观察过程、分布和确定性统计，选择要深入的范围与对象 | 改善 overview，开放必要的范围与聚合选择，让用户问题不再被固定榜单限定 |
| `trajectory_read` | 读取原文和有关联的执行片段 | 复用原始事件读取，增加有界关联阅读及长正文可靠续读 |
| `trajectory_graph` | 解释已有的替换、引用、派生和会话关系 | 在需要这类关系时直接使用，不另造一套关系接口 |

不为五种诊断分别增加工具，也不为构成、注入、回执、Skill 再建一组平行入口。现有证据适配器在内部复用，相关细节通过 inspect/read 取得。

两种方向暂不采用：

- 按统计项不断增加小工具：模型更难选择，声明与语义容易重复，读取同一片段还需多次往返。
- 一次性设计任意过滤、表达式、连接和聚合的通用查询语言：查询与校验成本会落回模型，也很难维持可靠的默认口径。

现有 `search(view=cost)` 与 `inspect(view=cost)` 有职责重叠。新分析方法统一引导至 inspect；兼容期保留旧入口，在内部逐步共用用量提取与口径校验，不要求模型把两套结果重新拼账。这不是现在就删旧接口。

## 7. 必要自由度：先支持几种有意义的操作

不先堆出一份很长的参数表。先用以下查询任务验收接口，再决定最小参数集合；下表是拟议能力，当前并非全部已实现。

| 查询任务 | 所需自由度 | 控制复杂度的方式 |
|---|---|---|
| 看整段任务怎样推进、投入分散在哪里 | 有界时间顺序总览、窗口/轮次分布和继续细看的入口 | 用真实用户要求与答复的短摘录、产物位置及官方统计；大范围分层查看，不只返回最大几步 |
| 从全程进入自己选择的一段 | 同一日志切点下自由改变轮次范围 | snapshot 固定日志修订，范围属于查询，不把二者绑定成一种含义 |
| 看某个工具、文件或有记录归属的来源 | 按明确对象过滤，并跨轮观察 | 返回可复用的对象标识；未知归属不猜测；对象查询沿用相同统计与读取能力 |
| 比较累积负担与单次尖峰 | 在少量有效维度上分组，并选择时间顺序或相关指标排序 | 每个 view 只支持有意义的维度和排序，不设计任意表达式；已有默认榜单可保留 |
| 对照调整/压缩前后，或两次相似尝试 | 对两个指定范围作口径一致的查询 | 先复用两次 inspect；不为前后对照新增工具或通用 join |

overview 应让模型有机会认识普通阶段和合理投入，不能再次变成另一张 Top N。长会话采用可展开的粗粒度窗口；窗口是查看方式，语义阶段仍由模型判断。统计区间内用户暂停、模型执行、工具累计与覆盖时间按实际口径区分。

同一 snapshot 下可改范围，需要将“冻结日志身份”与“范围索引”分离。复用紧凑统计与关系索引，范围结果按需生成，保留现有缓存预算与释放机制；不为每个参数组合保留完整日志或所有主题的副本。

## 8. 关联阅读怎样减少工作量

以一次操作或一个步骤为锚点，返回一小段连贯材料：

> 当时的用户要求/当前问题 → 实际调用 → 返回和任务状态 → 模型随后怎么处理；涉及历史更新时再带相关变化及请求回执。

使用 callId、rootCallId、正式结果、轮步和现有关系链做确定性关联。没有显式关联的后续消息只标为时间上的后续，不自动判定因果。跨越较远事件的操作不靠固定 ±2 或 ±5 个 seq 拼接。

默认保留工具名、关键参数定位、成功/错误/后台状态、job ID、结果要点和后续动作。内部执行结果与正式给模型的返回在有差异时并列呈现。这样既有助于解释任务，也能发现状态传递是否完整。

长流记录、重复传输片段和巨大正文不全部塞入首屏。每项省略都能回到同一版本的原文：明确字段/位置、规模和可直接调用的续读参数。用户随时看完整参数和正文的路径仍然保留，续读不要求重新搜索。

具体接口优先扩展已有 read 的返回方式，复用既有 seq/from/to/snapshot；正文的字段读取与分页只补必要能力。最终参数须结合真实调用试验收敛，本文不把试跑脚本的所有选项直接变成公开 schema。

## 9. 提示词与数据各放哪里

- **工具定义**：用途、动作、参数契约。模型无需预先阅读内部统计实现。
- **查询 skill**：怎样选择已有入口，以及引用和范围的共同规则；保持简短。
- **按需场景方法**：本场景的正面分析方法和对照方式；首次取得后使用清晰版本引用，不随每页重复返回。
- **查询结果**：事实、来源、范围、必要说明、对象标识和续读入口；不把每条数据都包装成长篇免责声明。
- **报告要求**：一份人能读懂的表达规则；不在每个工具或场景方法重新复制。

需要同时修正两类底层问题：`request/context` 元数据变化不能继续命名成请求/曝光累计；空搜索只表明本次范围和过滤下未命中，不能笼统保证整份历史不存在。这些应在实现和共同契约中解决，不能不断加长场景提示来补救。

## 10. 文字报告怎样才有用

正文先回答用户：这次主要表现是什么，为什么优先处理它，下次具体改变什么。随后用少量有代表性的事实支撑，并区分当前模型、用户配置与插件开发各能执行的动作。详细事件编号、方法口径和非关键限制放在证据部分。

例如，以下只是报告写法示例，不是对试跑会话的新结论：

> 这类任务可以先改能力发现的方式：先给简要接口索引，在选中接口后再取得完整签名，减少每个阶段都处理整份目录的工作。先在一次同类任务中试用，检查模型能否直接找到正确接口、是否增加补查和参数错误，再结合真实输入用量决定是否推广。

有不确定性时，把它落到决策上：什么条件会让建议改变，验证哪一点即可。正文不要求反复列“不能证明”的清单，也不以“缺少完整因果证据”回避可以成立的流程判断。

## 11. 怎样检验这次设计

先验收诊断质量，再验证建议收益，两者分别记录。

诊断质量的主要问题：

1. 选中的问题是否影响任务主要投入、推进或结果？有没有遗漏用户更关心的过程？
2. 是否解释了问题为什么持续、哪些做法值得保留，而非只报告一次异常？
3. 用户是否能清楚选择下一次要改的动作、对象和优先级？
4. 普通用户能否读懂结论与理由，且不必先学会内部事件名？

事实、范围、原文和计量正确是基础验收项。基础错误需要修正；仅通过这些检查，也不能算诊断有效。不用模型自评或单一健康分替代人工阅读。

工具效率同时比较：首轮定义/发现文本 token、整次分析输入输出、查询次数、重复与补读、失败调用及耗时。62–97 次试跑查询只说明存在摩擦，不能单靠调用数决定接口优劣；增加少量有用的邻近上下文，可能降低总工作量。

建议本身按场景验证：保持任务验收和必要能力，比较相关等待、输入输出、错误、补读或恢复成本。对于有随机性的任务，先做少量同类验证，再根据问题的重要性扩大样本。不预先承诺收益比例。

后续试验应先固定现有工具比较方法，再固定方法比较查询改进，以免把提示和工具同时变化产生的效果混为一谈。被用于设计的旧样本与后续未看过的验证样本分开。

## 12. 实施顺序

1. 修正已知计量/空结果契约，统一可以共用的事实提取；不扩张工具数量。
2. 优先改善有界过程总览与关联阅读，使模型能看全局、看懂局部。
3. 按真实分析任务补必要范围、对象和分组选择；继续复用现有四入口，不一次设计完整查询语言。
4. 将正面分析方法和简洁的报告要求接入，再在原生工具上评估有用性与总工作量。
5. 对值得采用的建议做具体任务验证；HTML 报告、自动操作及新可视化随后考虑。

本稿之后已实现过程总览、关联阅读、同切点范围切换、对象聚焦与有限分组排序，并替换按需分析方法。实验反馈后继续收紧默认返回。构成/注入/回执适配器没有另注册一组平行工具，效果建议也未自动执行；安装与实际模型协议接入仍与仓库测试分开。
