# 诊断方案 v2：三会话可用性试跑

日期：2026-10-30。用户指定使用 gpt-6.1-terra、max 子代理，三名子代理分别分析一份冻结的 DSH 对话。三份报告均已完成；长对话代理曾因所选模型容量不足中断，随后保持同一模型设置续写。

**用户评审结果：未达到诊断价值要求。** 用户指出报告偏重“不能推出什么”，缺少对任务本身的重要判断和改变下一次行动的建议，表达也不够适合普通用户阅读。以下保留事实与工具试验记录，不据报告完成、引用准确或查出局部缺陷宣称方法有效。后续设计见 [方法与工具设计复盘](diagnostic-method-and-tools.md)。

本轮检验的是方法能否引导具体取证、解释和行动。没有进行原生 DSH 工具协议集成测试、模型基线比较或建议收益复跑，不能据此声称诊断准确率、节省费用或改动收益已经得到验证。

## 得到的主要结论

### 1. 长期研究：状态传递比“输出是不是空”更值得检查

第 260 轮，内层 PowerShell 调用在超时后明确报告后台 job ID，模型编写的包装程序只提取 stdout，正式返回成了空 out；随后模型推测失败并启动重跑。关键原文为 seq 17445、17446、17460、17468。这给出了具体可改对象：包装代码应保留后台状态、job ID 和退出信息，状态不明时先核对原作业。

这个发现结合了工具内外层返回、模型能见的正式历史、压缩边界和后续行为，没有把“工具日志里有状态”等同于“模型已收到状态”。实际 CPU 重叠和可节省时长未被量化。

第 305 轮的压缩片段则作为取舍保留：请求回执显示缓存读取占比约为压缩前 99.9%、压缩后 3.6%、下一请求 99.7%（seq 19380、19398、19409）；后续局部编译工作也继续了。一次缓存下降不足以支持取消压缩，应该评价完整后续窗口。

### 2. 插件修复：区分计算、自检、路由和浏览器验收

两次宽范围目录搜索在 120 秒后转后台，随后被取消（seq 574、578、3353、3357）。其中一次还与已通过的包自检绑在同一个调用里。可改的是搜索范围、前置定位与命令拆分，不是把所有工具执行都改成并行。

另一组迭代显示，语法/打包或局部计算测试不能替代真实加载路径：后续路由仍返回 500 及未定义 helper，保存页浏览器探测又暴露 offset TypeError（seq 10211、10227、10578）。冻结在用户中止时，没有后续候选修复的成功验收。报告将这些不同层次的证据分开，并未把多次版本变化一概判为空转。

编辑保护报错后补读文件、随后编辑成功，被保留为有进展的重试。上下文可见性用作解释剖面，没有独立报一项“组装问题”。

### 3. 界面适配：区分检索命中与已核验的依据

第 26 轮的可见调用返回 Lean 路径和最多 20 条匹配声明行，随后答复称已读对应 Lean，并给出确定的理论到实现映射（seq 3513、3516、3525）。报告建议定点补齐声明、前提和证明，再核对映射条件；没有据此断言数学映射必然错误，或整个历史从未接触相关材料。

服务发现窗口还出现大目录、spill 补读，以及同时包含“未收录”与 10 秒超时的反馈。候选行动是索引与详情分层返回、区分明确失败和真正未响应；同时保留未知服务的发现入口和完整签名获取。

用户明确要求的通篇阅读，以及代码/截图改变之后的复查，均作为合理投入保留。

三份报告的关键原文可以定位，部分已发现的流程问题和工具缺陷也可复核。这些是事实层的结果；用户评审没有认可报告的整体诊断价值，不能把可复核性等同于解释有用、问题优先级正确或建议值得采用。

## 已确认并修复的真实工具问题

子代理发现 io 项的 seq 被相邻步骤的 seq 覆盖。真实案例中，条目显示 seq 3410，原文是 step/start；实际调用是 seq 3415，结果是 seq 3416。

源码原因是构造 IO 项时，末尾展开的 neighbours 覆盖了调用锚点。仓库现已：

- 保持 seq 指向真实调用，另外提供 callSeq 和 stepSeq；
- 将两类锚点纳入原文读取指针；
- 增加针对原生调用/Code Mode 调用与步骤定位的回归检查。

`node plugin/trajectory-tools/inspect-test.mjs` 通过，包括官方统计一致性、原文身份、分页和新定位断言。修复发生在报告完成后，没有重建本轮冻结索引；报告观察到的原始缺陷仍可复核。尚未将该改动安装进 DSH。

## 桥接缺口与子代理反馈校正

原生 InspectionService 已提供 reads，trajectory_graph 也已存在；本地桥仅使用 inspectionPage，没有暴露这些入口。子代理对此的反馈是本轮包装覆盖不足，不能当成产品缺少这些能力。

原生 trajectory_search 的 events 同样是字面检索，并有归一化、过滤及现有排序。部分子代理反馈中“原生语义搜索/排序”的说法不准确。此次差异主要是桥没有复刻这些行为，不据此提出必须新增语义搜索的需求。

长对话代理开始时误读过含有此前案例信息的接口文档。它已主动披露，随后从冻结日志重新核验；本轮不称盲测。

此外，request/context 被当作请求/暴露样本的命名与累计推断是试跑前已知限制，本轮明确禁止用于费用推算，尚未在源码中完成那组字段的正式修正。

## 下一轮优先修改

本节记录试跑刚结束时的局部改进项。用户后续反馈表明仅调整阅读和停止条件不够；方法、工具与验收目标应先按 [设计复盘](diagnostic-method-and-tools.md) 重新确定，再选择实现项。

1. **先让证据片段更完整。** 提供有界的“用户/状态变化—调用—内外层结果—后续请求/回执”读面，默认省略长流记录，必要正文仍可直接补读。复用原生 reads/graph，避免另造入口。
2. **收紧方法的停止条件。** 初筛后聚焦少数执行窗口；事实、最关键的替代解释和验证动作已经成立时收束。没有必要为了填满剖面或每个主题继续查询。
3. **减少重复提示返回。** 首次返回对应方法和共同输出规则；后续同方法分页保留版本/引用，避免一再返回整段说明。
4. **补齐真实挂载验证。** 修正已知统计口径后，把选定能力接回原生工具，再重复类似试跑，观察定位成功、必要补读和报告质量。

没有专门检验 Skill 效果对照，也没有复跑任何优化建议；不把三个案例外推成所有 DSH 任务的结论。
