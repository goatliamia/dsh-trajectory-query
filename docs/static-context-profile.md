# 当前上下文静态剖面：构成、使用与能力

日期：2026-10-30。状态：分析设计与源码研究，尚未新增静态查询 view。当前取证工具仍为四个入口；本次只加强现有诊断方法中的能力保持要求。

## 1. 要回答的问题

在一个明确切点，解释当前模型看到什么、这些材料支持什么工作、当前负担是否合理，以及哪些调整值得考虑。历史使用为这个状态提供背景，不能把“未调用”直接变成“可删除”。

优化的前提是保持用户需要的任务能力与结果，再比较总开销。工具语义改变可能缩小覆盖、改变结果解释或错误恢复，使某些真实任务更差；因此节省的声明或返回体积不能单独构成改动理由。

## 2. 静态剖面的内容

| 内容 | 对用户的意义 |
|---|---|
| 当前构成 | 系统、工具声明/SDK 目录、用户材料、技能、助手历史、工具结果等，分别保留既有估算与实报占用 |
| 当前有效能力 | 当前会话/Agent 实际可见的直接工具与 SDK；可发现、待生效、隐藏、不可用的能力另外说明 |
| 实际使用 | 指定观察范围内，同版本能力被怎样调用、处理什么对象、得到什么反馈、是否需要补读或恢复 |
| 保留价值 | 常用能力、关键低频能力、合理的完整返回、任务必须的覆盖与恢复路径 |
| 调整判断 | 具体冗余与无效往返；候选改变了什么、影响哪些场景、如何保持原任务结果 |

切点和使用窗口分别标注。当前配置不能与全会话所有历史版本混算；模型没有看到的全局注册项也不算当前输入。Code Mode 的单个 run_code 入口不等于只有一种能力，SDK 目录及其激活状态同样要纳入。

只读诊断不为盘点能力而触发加载器、执行文件操作或改变工具配置。使用已有公开快照/诊断状态；没有记录的归属或延迟加载状态保持明确来源。

## 3. dsh-ops 的实际差异案例

研究对象为 [T-Auto/dsh-ops](https://github.com/T-Auto/dsh-ops)，核对主分支提交 `3882e69c548a1094028fddfde0f7783f06f598fa`。官方对照是本机 `@deepseek-ai/dsh-tool-fs-search` 0.2.2-alpha.2 源码；这是指定版本的契约对照，不是对所有版本或整个项目效果的评价。

### 搜索覆盖和 pattern 含义确实不同

本机官方 glob 明确包含隐藏和 ignore 文件，并将不含分隔符的 `*.ts` 解释为任意深度的 basename 匹配。dsh-ops 的声明将 pattern 改为数组，`*.ts` 仅匹配根层；同时排除隐藏目录和依赖/构建目录。

因此即便把旧字符串机械包装成数组，也不保持原来的查找行为。定位深层源码、隐藏配置或依赖实现时，可能少返回恰好需要的文件。少返回不是对同一结果的纯粹压缩。显式换根目录或改用其他入口可能取得材料，但会改变发现流程，不能宣称原能力无损替换。

来源：[替换映射](https://github.com/T-Auto/dsh-ops/blob/3882e69c548a1094028fddfde0f7783f06f598fa/src/capabilities/replacements.ts)、[参数和行为声明](https://github.com/T-Auto/dsh-ops/blob/3882e69c548a1094028fddfde0f7783f06f598fa/src/capabilities/file.ts)、[搜索覆盖](https://github.com/T-Auto/dsh-ops/blob/3882e69c548a1094028fddfde0f7783f06f598fa/docs/search-coverage.md)。官方本机依据为 dsh-tool-fs-search/lib/index.js 的 buildGlobCommand 与 glob 参数定义。

### 返回状态与调用方式会影响完成能力

dsh-ops PTC API 使用 Outcome 值承载 completed、partial、error、conflict 等状态；只靠 try/catch 的旧调用逻辑可能漏掉返回值中的失败。搜索还区分扫描覆盖、页面覆盖及完整快照。只看“工具返回成功”或“这一页读完”会误判工作已完成。

来源：[PTC 结果契约](https://github.com/T-Auto/dsh-ops/blob/3882e69c548a1094028fddfde0f7783f06f598fa/docs/ptc-outcomes.md)。这属于调用契约变化，需同步验证模型的调用与失败恢复，不能只比较 JSON 更短或工具次数更少。

### 可发现、已激活与本轮可用不是同一状态

PTC SDK 按需加载要求在步骤边界后才生效；加载请求不使新绑定立即出现在当前冻结 SDK 中。不同模式和 Agent 作用域的暴露不同。因此静态工具数要读实际组装和激活状态，不按安装包总清单或预设名称推断。

来源：[SDK 加载](https://github.com/T-Auto/dsh-ops/blob/3882e69c548a1094028fddfde0f7783f06f598fa/docs/ptc-sdk-loading.md)、[作用域诊断源码](https://github.com/T-Auto/dsh-ops/blob/3882e69c548a1094028fddfde0f7783f06f598fa/src/integration/diagnostics.ts)。项目本身提供了这些区分，也专门说明声明体积测量不能代替任务收益验证，见 [PTC 开销研究](https://github.com/T-Auto/dsh-ops/blob/3882e69c548a1094028fddfde0f7783f06f598fa/docs/ptc-cost.md)。

这些差异足以否定“换成更短的 OPS 工具自然更高效”的默认建议。某一组合是否更适合用户，仍取决于具体任务需要的覆盖和完成结果。

## 4. 建议的门槛

| 调整类别 | 必须说明什么 |
|---|---|
| 表达精简 | 删除了哪项已确认重复；参数、默认值、约束、状态与恢复信息如何保留 |
| 暴露/加载变化 | 用户所需能力如何被发现、何时可用；是否增加查找、等待、错误与缓存改写 |
| 接口/执行语义变化 | 参数、匹配范围、结果/完整性、版本与错误恢复改变了什么；哪些任务会受影响 |
| 停用/替换能力 | 为什么符合用户工作范围；关键低频任务怎样继续完成；如何回退与验收 |

测试选择从差异出发。例如 glob 的深层匹配与隐藏配置、搜索截断后能否补齐依据、失败值是否被正确处理、加载后当前步/下一步是否可调用。比较最终结果、遗漏、恢复步骤和总输入/输出；不将能力减少所得的体积降低记作同能力提效。平均表现还需结合用户不可接受的关键失败场景。

方法可以给出明确的“保留”判断，不必强行凑优化项。例如：某组声明较大但承担需要的发现范围，当前使用低频也不足以支持删除；先保留它，检查是否存在真正重复的说明或往返。

## 5. 报告表达与接入

静态报告按“构成—作用—使用—判断”组织。每项建议带上具体变更、受影响场景与验证状态；保留合理开销及关键低频能力。图表可以按体积排序，但不能把大、低频或未调用直接着色为待移除问题。

能力保持要求已加入 inspect-methods.js 的共同报告规则及成本分析方法。静态剖面的取证仍需用准确的当前作用域组装补齐；现有历史 schema 清单不直接冒充当前完整工具面。后续优先扩展 inspect/read 的已有查询和证据适配，不新增平行工具体系。
